# DriveDrop iPhone and Android app — development foundation

**Not published, signed, or ready for store submission.** Kye requested both app stores on 7 November 2026 and confirmed that neither developer account exists yet and the business is an individual/sole trader.

This is an Expo SDK 58 / React Native 0.88 application. Expo Router provides native navigation. The existing DriveDrop web product remains the source of truth for bookings, payments, verification, evidence and messages.

## Implemented

- Native welcome, email/password sign-in, home, activity, account and delivery-summary screens.
- The existing DriveDrop vector icon rendered at 1024px; no new branding.
- Customer/transporter sessions stored in device SecureStore, scoped to the configured server origin. No passwords, address lists, messages or payment data are persisted in local application storage.
- Native delivery summaries and explicit directions actions opening the phone's mapping service. Addresses are shared with that service only when the user taps Directions.
- Read-only overview API returns the current user's active deliveries and recent notifications. It selects only required fields and reuses role-specific notification redaction. It does not expose payment-provider identifiers or the other party's financial totals.
- Controlled web screens reuse existing marketplace flows. Their session handoff uses an HTTPS POST body, not a URL, localStorage or injected JavaScript. Cross-site browser requests and unauthorised destinations are refused.
- Stripe destinations open the system browser rather than exposing the native authentication token to third parties. Payment and payout outcomes remain server-authoritative.
- Separate iOS/Android build profiles. The proposed application identifier is `com.drivedrop.app`; it has not been registered or reserved.

## Backend release control

All four `/api/mobile/*` endpoints are **disabled unless `MOBILE_APP_ENABLED=true`**. No production or preview environment value has been changed for this work. No migration is required: the revocable existing Session table stores hashed native tokens with a 14-day expiry.

Mobile sign-in preserves current website sessions, subject to a five-session cap. The website's existing `createSession` implementation still clears all sessions for that user when a new website login is created, so a website login can sign the app out. This behaviour must be reconciled and tested before release.

The existing login rate limiter is process-local. A shared rate-limit store is required before exposing the additional mobile login endpoint to production. Do not enable the production flag until authentication and handoff tests pass on real devices and this release requirement is addressed.

## Local checks

From the repository root:

```sh
node --test scripts/test-mobile-app.cjs
npm run typecheck
```

From `mobile/`:

```sh
npm ci
npm run check
npx expo install --check
npx expo export --platform ios --output-dir dist/ios
npx expo export --platform android --output-dir dist/android
```

Copy `.env.example` to a local env file and set `EXPO_PUBLIC_API_ORIGIN` to a reviewed HTTPS DriveDrop preview for pre-release testing. It is a public origin, not a credential. Never put keys or tokens in `EXPO_PUBLIC_*`. Token storage is separate for each origin. Existing preview deployment protection must be handled through authorised access, not disabled to make the app work.

Native projects are generated by Expo Continuous Native Generation; do not hand-edit `ios/` or `android/`. Native compilation/signing requires the owner's Expo project and store credentials or the relevant native SDK environment. JavaScript bundle exports are not installable IPA/APK/AAB files and are not proof of device behaviour.

## Remaining before store submission

1. Register developer accounts in the correct legal capacity and establish the owner's Expo build project. Do not create a company identity for a sole trader, invent a D-U-N-S number, accept agreements, purchase memberships or register identifiers without the owner's appropriate involvement.
2. Implement actual account/data deletion. `/api/account/close` currently marks the user `DELETED` and revokes sessions but retains user fields, photos, messages and documents. That is not evidence of compliance with Apple/Google deletion requirements. Provide an easily found in-app deletion path and a public web request URL, with a clear, reviewed retention process for booking/transaction/dispute records. Existing public wording has not been edited.
3. Reconcile website/native session coexistence, add distributed login rate limiting and verify session expiry, revocation, secure storage, cross-account isolation and WebView POST/cookie behaviour on iPhone and Android.
4. Complete native device QA: safe areas, keyboard, text scaling, accessibility, Android back behaviour, account creation, password reset, photo/PDF uploads, camera permissions, proof-of-delivery GPS permissions/denial, receipt download/sharing and external links.
5. Verify Stripe Checkout/Connect and bank-authentication returns in the app using the appropriate non-production environment. Browser dismissal is not proof of payment. Do not repeat completed financial recovery tests or create dummy real-card charges. The first genuine live booking remains the separate live-flow verification opportunity.
6. Review the app's utility against Apple's minimum-functionality requirement; native navigation and summaries alone do not guarantee approval. Push notifications, offline delivery reports, native evidence capture and universal/app links are **not implemented** and must not be advertised as available.
7. Complete privacy disclosures, App Privacy/Data Safety forms, age rating, reviewer accounts/instructions, screenshots from real app builds and store metadata. The current website policy and closure behaviour must be reviewed for the actual mobile data flows; no compliance claims are made here.
8. Run TestFlight and Google Play testing, then submit signed builds for review. No store listing, paid account, signing key, tester invitation or submission has been created by this change.

## Owner registration route

- **Apple:** Individual enrollment for a sole proprietor. The seller/developer is the owner's personal legal name; the app itself can be named DriveDrop, subject to availability. Apple lists US$99 per membership year, with local pricing during enrollment. Start: https://developer.apple.com/programs/enroll/
- **Google:** Google's current account-type guidance directs commercial/business apps to an organisation account and requires a D-U-N-S number. Verify the sole-trader business identity through the actual enrollment process before paying; do not invent a limited company. The Play Console registration fee is US$25 once. If a personal account is determined appropriate, new personal accounts require at least 12 opted-in testers for 14 continuous days before applying for production access; this is not a reason to misclassify the account.
